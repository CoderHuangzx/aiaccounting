# AI 记账 · 总体设计

> 版本：v0.1.1 之后整理。本文回答三个问题：**定位是什么、现在怎么搭的、接下来补什么**。

---

## 1. 产品定位

**一个人的账本，不是一个记账平台。**

| 维度 | 选择 | 理由 |
| --- | --- | --- |
| 用户 | 只有我 | 不做多用户、不做登录、不做社交 |
| 数据 | 全部本地 SQLite | 无服务器、无账号、无上报；换机靠导出/云备份 |
| 输入 | 手动 + 自动捕捉 + 账单导入 | 三条腿，任何一条断了账本还能用 |
| 判断 | **宁可漏判，不可误判** | 一条错账比十条漏账更伤信任；自动结果一律先进「待确认」 |
| 成本 | 0 元 | 不用付费 DB / 云服务；云备份用坚果云免费额度 |

### 设计原则（落到代码里的）

1. **不可逆操作要显式确认**：删除有二次确认，导入覆盖有预览。
2. **自动化的产物都不直接入账**：`status = PENDING` → 用户确认 → `CONFIRMED`。主列表只查 CONFIRMED。
3. **同一笔账只存一份**：三路来源用 `dedupKey` 指纹归一（`ch:<单号尾8>` / `auto:<金额>:<10分钟窗>:<商户>`）。
4. **规则可回溯**：通知原文进 `raw_captures`，捕捉日志可查；否则「为什么这笔没记上」永远查不清。
5. **系统限制写进代码注释**：MIUI 杀后台、Android 17 测试限制、通知折叠等，都在对应文件里注明。

## 2. 现状（v0.1.1）

```
用户操作
  ├─ 记一笔（键盘 / 日期滚轮 / 分类 / 账户 / 备注）
  ├─ 点条目编辑 / 删除
  ├─ 搜索（分类·商户·备注·账户·金额）
  └─ 报表（周/月/年，趋势 + 分类占比 + 环比）

自动输入
  ├─ 通知捕捉（微信/支付宝/淘宝/京东/美团/抖音）→ 待确认收件箱
  └─ 读屏记账（淘宝/京东/抖音/美团订单页）→ 待确认收件箱

批量输入
  ├─ 支付宝 CSV 导入（GBK 自动识别、交易号去重）
  └─ 微信 XLSX 导入（自解 zip+XML、Excel 序列号还原）

数据出口
  ├─ CSV 导出 / 导入（SAF）
  └─ WebDAV 云备份（坚果云，可自动备份）

辅助
  ├─ 商户 → 分类自学习（改一次分类就记住）
  ├─ 捕捉日志（原文 + 是否匹配 + 原因）
  └─ 隐形 overlay 锚点（保持"在其他应用上层"状态，划掉后台仍在）
```

## 3. 架构

```
┌─────────────────────────────────────────────────────┐
│ UI  : Compose（Material 3，自建蓝白主题）             │
│  AppRoot ─ 首页 / 报表 / 记账面板 / 设置（含子页）      │
│          └ 收件箱 / 捕捉日志 / 云备份 / 导入教程       │
├─────────────────────────────────────────────────────┤
│ ViewModel : HomeViewModel / ReportViewModel /        │
│             EntryViewModel（StateFlow 单向数据流）     │
├─────────────────────────────────────────────────────┤
│ domain : 纯逻辑，可单元测试，不依赖 Android            │
│   Money / AmountInput / DedupKey / HomeGrouper       │
│   ReportPeriods / ReportCalculator / DateTimeDraft   │
│   BackupCsv / CsvCodec / HomeFilter                  │
│   PaymentParser / OrderScreenParser                  │
│   AlipayBillParser / WeChatBillParser / XlsxReader   │
│   MerchantMatcher                                    │
├─────────────────────────────────────────────────────┤
│ data : AccountingRepository（唯一写入口，事务）        │
│   Room（accounts / categories / transactions /       │
│         raw_captures / merchant_rules）              │
│   WebDavClient（HttpURLConnection + Basic Auth）      │
├─────────────────────────────────────────────────────┤
│ 系统集成                                              │
│   NotificationListenerService（通知捕捉 + 补捞）       │
│   AccessibilityService（订单页读屏）                   │
│   ForegroundService + 1×1 overlay（状态保持）          │
│   BootReceiver（开机/覆盖安装后拉起）                   │
└─────────────────────────────────────────────────────┘
```

**分层约束**：`domain` 不许 import android.*；`data` 之外不许直接碰 DAO；所有写入走 `AccountingRepository`。

## 4. 数据模型

| 表 | 关键字段 | 说明 |
| --- | --- | --- |
| `accounts` | name | 微信 / 支付宝 / 现金 / 银行卡 |
| `categories` | name, kind(EXPENSE/INCOME), emoji, sortOrder | 10 + 5 个内置分类 |
| `transactions` | type, amountCents, occurredAt, categoryId, accountId, merchant, note, **source**, **dedupKey**, **status** | 金额存分；source = MANUAL/NOTIFICATION/IMPORT；status = PENDING/CONFIRMED |
| `raw_captures` | packageName, title, text, capturedAt, parsed, reason | 通知原文留档，调规则用 |
| `merchant_rules` | pattern(唯一), categoryId, hitCount | 商户→分类学习结果 |

### 三路来源如何归一

```
手动记账      → dedupKey = null（不去重）
通知捕捉      → ch:<单号后8位>  或  auto:<金额>:<10分钟窗>:<商户>
读屏记账      → 同通知
账单导入      → <交易号>，命中则跳过
```

导入时还有第二道判重：`金额相同 + 时间差 10 分钟内`。两道都过不去才落库。

## 5. 关键机制

### 5.1 服务保活（MIUI 环境下的现实做法）

| 层 | 机制 | 抗什么 |
| --- | --- | --- |
| 通知监听 | 系统绑定，被回收后自动重绑，`onListenerConnected` 里补挂窗口 + 补捞 15 分钟通知 | 划掉后台 |
| 前台服务 | `startForeground` + `stopWithTask=false` + `START_STICKY` | 系统内存回收 |
| 开机/覆盖安装 | `BootReceiver`（BOOT_COMPLETED / MY_PACKAGE_REPLACED） | 重启、升级 |
| 手动强停 | **无解**，任何第三方 App 都躲不过 | — |

### 5.2 权限矩阵

| 权限 | 用途 | 不给的后果 |
| --- | --- | --- |
| 通知使用权 | 捕捉支付通知 | 自动记账完全失效 |
| 无障碍 | 订单页读屏（下单即记） | 抓不到 App 内下单 |
| 显示在其他应用上层 | 保持状态提示 | 状态消失，无功能影响 |
| 自启动 / 电池无限制 | 后台存活 | 划掉后台后被彻底清理 |

## 6. 缺口分析

按「对正确性的影响」排序，而不是按「做起来爽不爽」。

### A. 正确性缺口（会算错账）

| # | 缺口 | 现状 | 影响 |
| --- | --- | --- | --- |
| A1 | **转账被记成支出+收入** | 微信↔支付宝互转会污染统计 | 月度收支虚高 |
| A2 | **退款不冲抵原单** | 退款记独立收入 | 支出虚高（已决定暂不做） |
| A3 | **去重靠时间窗** | 通知+导入同一笔若差 10 分钟以上会重复 | 偶发重复 |
| A4 | **读屏金额依赖标签** | 页面改版就没标签 | 漏记（可接受） |

### B. 可用性缺口（用起来别扭）

| # | 缺口 | 说明 |
| --- | --- | --- |
| B1 | **没有自检页** | 权限掉了、服务被杀了，用户不知道；跑一段时间收集数据时这是最大风险 |
| B2 | **分类不能增删改** | 固定 15 个；自学习规则也只能写不能看/删 |
| B3 | **没有账户余额** | account 只是个标签，看不出「钱在哪」 |
| B4 | **批量操作缺失** | 收件箱只能一条条确认；改了规则也没法批量重分类 |
| B5 | **按来源开关** | 3.0 目标，见路线图 |

### C. 体验缺口

| # | 缺口 |
| --- | --- |
| C1 | 桌面小部件 / 快捷方式（参考图里有） |
| C2 | 预算与超支提醒 |
| C3 | 月度对比（和上月、去年同月） |
| C4 | 筛选器（按来源/账户/金额区间） |
| C5 | 截图记账（参考图里的「截屏记账」，需要 OCR 或 LLM，成本高） |

### D. 工程缺口

| # | 缺口 | 影响 |
| --- | --- | --- |
| D1 | **没有 CI** | 改动靠本地跑测试，容易漏 |
| D2 | **还是 debug 签名** | 不能上架，重装可能丢数据（同签名才行） |
| D3 | 云备份只在 App 运行时触发 | 长期不打开就不备份 |
| D4 | 没有崩溃日志 | 真机出问题只能靠 adb 抓 |

## 7. 路线图

### v0.2 —— 稳定性（跑数据期间最该补的）

- **自检页**（B1）：一屏显示通知监听器在线状态、无障碍开关、overlay 权限、电池优化、自启动建议、最近一次捕捉时间，每项可一键跳转
- **分类管理**（B2）：增删改分类 + 查看/删除已学习的商户规则
- **崩溃自留档**（D4）：未捕获异常写本地文件，设置里可导出

### v0.3 —— 输入侧可控（对应 3.0 的截图）

- **按来源开关**：设置 → 自动记账 改成来源列表（短信/微信/支付宝/淘宝/京东/美团/抖音/小米支付/截屏/账单导入），关掉的不监听、不留日志
- **转账类型**（A1）：新增 TRANSFER，转账不计入收支统计
- **批量操作**（B4）：收件箱批量确认 / 批量忽略

### v1.0 —— 账本完整

- **账户余额**（B3）：期初余额 + 自动累计，首页显示总资产
- **对账视图**（A3）：把同一时间段的「通知捕捉」和「账单导入」并排对比，手动合并
- **预算**（C2）+ **月度对比**（C3）

### v3.0 —— 智能化（成本敏感，按需）

- 截图记账（C5）：优先考虑端侧 OCR，避免长期 API 费用
- 自动分类：从「商户精确匹配」升级到「商户 + 金额 + 时段」的轻量模型
- 小部件 / 快捷方式（C1）

## 8. 风险清单

| 风险 | 概率 | 对策 |
| --- | --- | --- |
| 支付 App 改通知文案 | 高 | `raw_captures` 留档 + 捕捉日志，改规则不用重新抓包 |
| MIUI 收紧后台限制 | 中 | 前台服务 + 系统绑定服务双保险；自检页暴露掉线 |
| 电商 App 改版导致读屏失效 | 中 | 只认「标签 + 金额」的保守规则，改版时表现为漏记而不是错记 |
| 数据丢失 | 低 | 本地 CSV + 坚果云双备份；导入前先导出 |
| 账单文件格式变化 | 中 | 解析失败时给出明确错误（「第 N 行/缺哪一列」），不静默丢数据 |

---

## 9. 不做什么

明确排除，避免以后反复讨论：

- ❌ 多用户 / 登录 / 云同步账号
- ❌ 付费数据库、付费 OCR / LLM 接口
- ❌ 广告、会员、导出水印
- ❌ 自动点击 / 模拟操作其他 App（只读屏，不代操作）
- ❌ 上传任何账单原文到第三方
