# AI 记账 · MVP 范围（v0.1）

> 状态：已确认（2026-11-22）
> 定位：个人自用 / 单设备 / 单用户 / 无账号 / 无后端

## 一、本期已确认的边界

| 项 | 决定 |
| --- | --- |
| 使用场景 | 自用，不上架、不分发 |
| 截图记账 | 本期不做（依赖付费 LLM，暂缓到 V2） |
| 微信 / 支付宝自动记账 | 做「自动捕捉 + 人工确认」，不承诺全自动 |
| 美团 | 不单独适配（订单多走微信/支付宝，抓支付渠道即可覆盖） |
| 技术栈 | Kotlin + Jetpack Compose + Room + WorkManager |
| 数据 | 本地优先，数据不出设备，无云端、无账号 |
| 运行成本 | 0 元/月：所有解析在端侧完成，不调用任何在线模型 |

「AI」在本期的含义不是大模型，而是**规则解析 + 分类自动学习**：商户自动归类和用户改一次就记住的映射。真正的语义/截图理解留到 V2。

## 二、要解决的问题

自用的真实痛点是「记不住、懒得记、月底对不上」，因此本期只解决三件事：

1. 随手能记 —— 3 秒一笔
2. 大部分账能被自动捕捉到，人只做「确认」这种低负担动作
3. 月底能对账 —— 漏的能补回来

## 三、P0 功能（本期必须做）

1. **手动记账**：打开即键盘、默认支出、支持表达式（`12+8`）、最近商户一键复用、保存后原地可继续记、时间和备注可改。
2. **通知捕获（微信 + 支付宝）**：`NotificationListenerService` + 本地规则解析金额/方向/商户/时间，产出待确认记录，零网络依赖。
3. **待确认收件箱**：按来源标注（通知 / 导入 / 手动），一键确认、改分类、忽略、合并重复。
4. **账单文件导入**：解析支付宝 / 微信官方导出的账单文件，批量入库并与已有记录对账，产出「疑似重复 / 疑似遗漏」清单。**这是替代截图记账的对账安全网。**
5. **去重与归一**：三路来源（通知 / 导入 / 手动）汇聚到同一张流水表，靠幂等键收敛。
6. **交易列表**：筛选、搜索、按账户/分类/时间过滤。
7. **月度汇总**：支出 / 收入 / 结余、分类占比、简单趋势。
8. **分类体系 + 商户自学习**：内置商户关键词词典（星巴克、瑞幸、滴滴、美团、京东、话费、水电…），用户改一次分类即写入商户规则，下次自动命中。
9. **本地存储 + 导出备份**：Room + 每日自动导出 JSON 到本地目录，支持手动导出 CSV。
10. **权限与保活引导**：通知使用权、通知显示详情、忽略电池优化、厂商自启动白名单——直接决定自动捕捉能不能用，不能省。

P1（本期尽量）：桌面小组件 / 长按快捷入口直达记账键盘；按账户的余额视图。

## 四、明确不做

云同步与多设备、多账本、多币种、预算与超支提醒、家庭共享、iOS / Web 端、银行卡直连、全自动零确认、在线 LLM 语义记账、美团/饿了么单独适配、高级报表与投资分析。

## 五、关键技术判断

### 5.1 通知捕获的真实覆盖率是最大的未知数

通知监听只能拿到「App 在后台时系统弹出的通知」：

- **命中较好**：线上支付、自动扣款、订阅续费、跨 App 跳转支付（支付完成后支付 App 退到后台）。
- **很可能漏**：当面扫码付款——此时微信/支付宝在前台，支付结果在 App 内展示，可能根本不产生系统通知。

结论：**在写任何 UI 之前，先用 2 天做一个最小通知监听 demo 在真机上实测一周**，统计命中率。若低于 60%，W2 的重心从「通知」转向「手动提速 + 账单导入对账」，通知退化为增量补充。

另一个隐性依赖：用户必须在支付 App 里开启「通知显示详情」，否则通知里只有「你有一笔消费」没有金额。这条要写进引导页。

### 5.2 账单导入是安全网，不是可选项

支付宝、微信都提供官方账单导出（文件 / 邮件）。解析它：

- 零权限、零成本、覆盖 100% 的交易；
- 能补历史账，也能事后对账；
- 解析器版本与容错要做好，失败时保留原文件供手工处理。

对自用场景，这条路径的边际收益高于通知监听。

### 5.3 去重是刚需

同一笔消费可能同时来自通知、账单导入、以及你手动补记的一次。

- 幂等键优先用渠道单号（支付宝订单号 / 微信交易单号）后 4–6 位；
- 无单号时用「金额 + 方向 + 时间 ±10 分钟 + 商户前缀」生成指纹；
- 冲突时提供「合并」动作，而不是弹错误。

### 5.4 「AI 感」不靠大模型

内置商户关键词词典 + 用户纠正即学习，这套规则离线、可解释、可手工编辑，命中率可以做得很高，成本为零。

## 六、数据模型草案

金额一律用 `Long` 存「分」，时间存 epoch millis，展示按本地时区。

```
Account(id, name, type[CASH|ALIPAY|WECHAT|BANK], initialBalanceCents, archived)
Category(id, name, parentId, kind[EXPENSE|INCOME], icon, keywords, sortOrder)
Transaction(id, type[EXPENSE|INCOME|TRANSFER], amountCents, occurredAt,
            accountId, categoryId?, merchant?, note?,
            source[MANUAL|NOTIFICATION|IMPORT], externalId?, dedupKey,
            rawCaptureId?, status[PENDING|CONFIRMED|IGNORED], confidence?,
            createdAt, updatedAt, deletedAt)
RawCapture(id, source, packageName?, text, capturedAt, importBatchId?,
           parseStatus[OK|PARTIAL|FAILED], parseNote?)
MerchantRule(id, pattern, matchType, categoryId, hitCount, source[BUILTIN|USER])
ImportBatch(id, fileName, channel[ALIPAY|WECHAT], importedAt,
            rowCount, appliedCount, skippedCount)
```

`RawCapture` 必须留档：规则调歪了要能回溯原始文本，否则没法修。

## 七、迭代计划（约 4 周出 v0.1）

| 周次 | 内容 |
| --- | --- |
| W1 | 数据模型 + 手动记账 + 列表 + 月度汇总（先让 App 自己愿意用） |
| W1.5 | **通知捕获 spike**：最小 demo 真机跑一周，统计命中率 |
| W2 | 待确认收件箱 + 去重 + 权限/保活引导（按 spike 结果调整重心） |
| W3 | 账单导入解析 + 对账合并 + 分类自学习 |
| W4 | 导出备份 + 打磨 + 自己真实用一周跑数据 |

## 八、验收指标

- 手动记账 ≤ 3 秒/笔；
- 自动捕捉进入收件箱后，**无需修正直接确认的比例 ≥ 90%**；
- 重复与误报 ≤ 2%；
- 一次账单导入能把当月 ≥ 95% 的交易对上；
- 自用一周后不再需要「事后补账」。

## 九、风险与对策

| 风险 | 对策 |
| --- | --- |
| 厂商后台策略杀掉通知监听 | 引导页 + 自启动白名单 + 手动补记的极速入口 |
| 支付 App 通知文案随版本变化 | 规则表外置为 assets 里的 JSON，改规则不用改代码 |
| 三路来源重复记账 | 幂等键 + 合并动作，见 5.3 |
| 账单文件格式变化 | 解析器带版本号与容错，失败保留原文件 |
| 数据丢失 | Room + 每日自动 JSON 导出 + 手动导出 CSV |
| 前台支付漏抓 | 见 5.1，先实测再定权重，不假设它可用 |

2. 搭 Android 工程骨架：Gradle + Compose + Room + 手动记账闭环。
